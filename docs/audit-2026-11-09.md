# Pippin audit, 2026-11-09

Audited commit: `63743d7` (v0.41.1 plus docs). Machine: Apple M5 Pro, macOS 27.2.

## Method

1. Seven read-only audit passes, one per lens: security, reliability, data integrity, agent interface, performance, architecture, docs. Each returned findings with file and line, quoted evidence, a scenario and a proposed fix.
2. A skeptic pass re-read the cited code for every finding rated P0 or P1 (54 findings) and assigned a verdict.
3. A red-team pass tried to reproduce findings on throwaway objects only. Its results are in the Red team section.

Severity: P0 is data corruption, a security hole or a destructive-action risk. P1 is a reliability or correctness fault. P2 is performance or cleanup. P3 is a feature.

What the evidence is: unless a row says "reproduced", a finding was verified by reading the code path, not by triggering it. Triggering most of them would have meant writing to real data, which the audit did not do.

## The two bugs the mission named

### pippin-pvak (mail rows mixing fields), closed before this audit

Root cause, confirmed by reading the fix in `d8cf28d`: compound ids are `account||mailbox||ROWID`, Mail reassigns row ids after an index rebuild, and the body cache was keyed by compound id alone. An old body and header set were served under a new message's subject and date. Every cache read now takes the row's date and evicts on mismatch (`MailBridge/MailBodyCache.swift:95`).

The join and array-zip explanations in the original report were not the cause: the fast path is one `SELECT` with foreign-key joins, and the JXA parallel arrays are guarded by an id re-read and length checks.

Gaps the fix left, each now tracked: mutations are unchecked (pippin-h8ro), the identity is a date at one second resolution, and the sender baseline is still keyed by the reassignable id (both in pippin-xr89).

### pippin-lzuv (Messages unread count), open

Two mechanisms, both in `MessagesBridge/MessagesDatabase.swift`:

1. The count is over the whole history (`:156`, `:418`), while the messages returned are the newest `limit` rows (`:386`).
2. `is_read = 0` is not the same as unread. The Messages database leaves it at 0 forever on some inbound rows that have no text and no attachment.

Measured on the installed 0.41.1 across the 21 threads with a nonzero count (53 counted rows): 41 are returned at the default limit, 12 are not, and 19 have no text and no attachment. With a very large limit the count and the rows agree in all 21 threads, which rules out a join fault.

Fix: one shared definition of a displayable inbound message, used by list, show, search and the count.

## What was checked and found sound

These hold in the code as read, and are the basis for the guarantees the docs may state:

- Every string interpolated into a JXA script is escaped, and no command invokes a shell.
- Every SQL string value is a bound parameter.
- The Messages autonomous-send gate fails closed, and mail send previews unless `--confirm` is passed. `--dry-run` wins over `--confirm`.
- A send is never retried inside the command after a timeout.
- Every delete needs an explicit flag, and the MCP server refuses before spawning.
- `pippin do` never feeds tool output back into planning.
- `Package.resolved` pins exact revisions for both Swift dependencies.
- Subprocess pipes are drained concurrently, timeouts use SIGTERM then SIGKILL, job and session files are written atomically, and Pippin's own caches use WAL with a busy timeout.
- Apple's stores are opened read-only everywhere except `memos delete`.
